# ADR-0004：双 Hub 采用双节点单活动复制

- 状态：已接受，分阶段实施
- 决策范围：电脑 Hub、Android Mobile Hub、节点复制、当前 Hub 切换和故障恢复
- 详细实现：[双 Hub 复制与安全切换实现方案](../architecture/dual-hub-replication.md)

## 背景

ADR-0002 将电脑上的 AetherX Hub 定义为唯一写入者，手机是通过 REST 与 SSE 连接的客户端。这个模型简单可靠，但电脑关闭后，手机无法继续使用依赖 Hub 的聊天、记忆和工具能力。

AetherX 需要让手机拥有自己的完整数据副本和本地 Hub，同时继续保持自托管、无官方数据云、数据可验证和 SQLite 单机事务优势。

## 决策

同一个用户数据空间可以登记电脑和手机两个 Hub 节点。两个节点都保存完整业务数据和媒体，但正常情况下只有一个节点是当前活动 Hub：

- 活动 Hub 接受业务写入、运行 Agent 和执行后台任务；
- 备用 Hub 只接收复制、进行校验并保持接管准备状态；
- 业务变更通过事务内 Operation Log 复制，不复制活跃 SQLite 文件；
- 计划切换必须等待操作和必要媒体追平，并比较逻辑数据摘要；
- 原 Hub 不可达时只允许用户明确强制接管，不进行静默自动故障转移；
- 强制接管后发现的旧代次写入进入隔离和恢复流程，禁止通用 Last-Write-Wins；
- 局域网和 Tailscale 只提供传输路径，节点仍执行独立的应用层身份验证；
- Android 被系统停止后不承诺继续作为永久入站服务器，但用户打开 App 时手机 Hub 必须能独立工作。

## 原因

- 满足电脑关闭后手机仍可使用的核心需求；
- 保留单活动写入，避免钱包、消息、记忆和后台任务在两个节点重复或乱序；
- Operation Log 同时提供幂等、断线补拉、审计和缺口检测；
- 全量快照与增量操作分层，适合首次配对和长期实时复制；
- 内容哈希和逻辑根摘要能把“同步完成”变成可验证状态；
- 明确承认两节点网络分区的限制，不用时间戳覆盖制造虚假一致性。

## 后果

- 现有 `sync_changes` 继续服务客户端刷新，不能直接承担 Hub 复制；
- 所有业务写入最终都要迁移到 Replication-aware Unit of Work；
- Provider 密钥落库继续使用每个节点自己的本机主密钥，复制时必须使用 Space Data Key 生成实体绑定的加密信封，目标节点解封后重新进行本机加密；
- 媒体需要逐步迁移到内容寻址和分块传输；
- 客户端需要从单一 `serverUrl` 迁移到 Space、节点和 epoch 路由；
- Android 需要本地 Store、Keystore、后台协调器和 Hub Bridge；
- 强制接管可能产生需要人工处理的分叉，因此必须建设恢复中心；
- 在迁移完成前，ADR-0002 的单 Hub 行为继续作为默认兼容模式。

## 不采用

- 同时允许两个 Hub 任意写入后按 `updated_at` 覆盖；
- 使用 Syncthing、网盘或共享目录复制 SQLite/WAL；
- 默认引入通用 CRDT；
- 依赖 Tailscale 身份替代 AetherX 节点授权；
- 隐藏 Android 后台限制并承诺手机 Hub 永久在线；
- 两节点失联时自动选举并宣称不会分叉。
