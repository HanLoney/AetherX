# 双 Hub 当前进度与问题登记

本文记录双 Hub 功能当前已经完成的工作、真实设备验证结果、尚未解决的问题和后续验收标准。发布结论以本文的“发布阻塞项”和“最终验收标准”为准，不以单项测试通过代替完整闭环通过。

## 当前结论

- 双 Hub 的主状态机、数据复制、切换恢复和客户端路由已经完成核心修复。
- 电脑 Hub 与手机 Hub 已在无 USB、无 ADB forward/reverse 的同一局域网中完成真实往返切换，切换后两端数据序列一致。
- 手机客户端已确认会自动切换到当前活动的电脑 Hub，并能直接加载数据页，无需重新连接。
- 当前仍不能判定可公开稳定发布：全新用户流程和连续运行观察尚未完成，Windows 安装包未签名，当前真机也因已安装 Debug 证书包而无法无损覆盖正式签名包。
- USB/ADB 只能用于开发调试、安装和故障诊断，不属于正式产品连接方案，也不能作为发布验收通过的依据。
- 正式产品必须由应用自动选择局域网或 Anywhere 通道，用户不应输入地址，也不应连接 USB 数据线。

## 已完成的核心修复

### 切换状态机与故障恢复

- 修复电脑端停留在 `committing_switch`、手机端停留在 `integrity_check` 的半切换状态。
- 切换恢复流程会查询对端 `/api/v1/peer/status`，识别对端实际阶段。
- 本地缺失 `committing_switch` 阶段时可以补放该阶段。
- 对端已经提交切换时，本地可以继续完成收尾，不再重复失败。
- 提交响应丢失后可以幂等重试，避免一次网络抖动永久卡死切换。
- Android 本地 Hub 接受重复提交并按幂等成功处理。
- Android 启动恢复会区分本机发起和对端发起的事务，避免错误接管不属于本机的恢复流程。

### 错误信息与诊断

- `PeerTransport` 保留对端真实的 `5xx` 状态码和错误详情，不再全部转换成 `PEER_UNREACHABLE`。
- 新增对端状态接口，供切换恢复判断真实阶段。
- 增加提交响应丢失、恢复责任归属和对端错误透传测试。

### Android 原生备用复制

- Android Local Hub 原生实现 `/peer/hello`、`/peer/operations`、`/peer/acknowledgements`、`/peer/media/manifest`、`/peer/media/:id/blob` 和 `/peer/client-sessions/mint`，备用复制不再依赖前台 WebView。
- 客户端会话签发只读取 Android Keystore 加密的现有手机会话身份，不保存或复制密码。
- 电脑端备用复制查询手机 Hub 自己的 Operation 链，避免把电脑来源序列误判为手机复制进度。
- 跨网探测超时提高到 `5000ms`，端点选择优先使用最近探测成功的 Anywhere 地址，避免失效 LAN 地址阻塞可用链路。
- 桌面客户端拒绝低 epoch 路由覆盖；活动 Hub 的短暂就绪失败不会再把已持久化的较新路由回滚到旧 Hub。
- Android 业务桥接在 WebView 唤醒失败时仍会投递请求，并把无响应等待限制为 `15s`，避免桥接工作槽被长期占满。

## 当前发布阻塞项

### 尚未完成的发布验收

- 尚未从清空应用数据的全新用户状态完整执行安装、注册/登录、一体化配对、首次同步、切换和回切。
- Windows 安装包未配置受信任的代码签名，公开下载时会出现系统信誉警告；若决定无签名发布，必须把该风险写入发布说明。
- 当前真机安装的是 Debug 证书版本；正式 `lanRelease` 无损覆盖返回 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。在不清除用户数据的前提下，正式包覆盖升级验收尚未完成。
- 尚需连续运行观察，确认不会重复创建切换事务、出现假“已同步”或持续误报“连接异常”。

### 正式产品链路要求

必须满足以下连接策略：

1. 手机和电脑位于同一局域网时，自动发现并优先使用 LAN 地址。
2. 手机和电脑不在同一局域网时，自动使用 Anywhere 通道。
3. LAN 与 Anywhere 状态变化后，双方自动刷新端点并重新选择可达地址。
4. 用户不需要知道 IP、端口、Tailscale 地址或 Hub 地址。
5. 用户不需要插 USB 数据线。
6. 任一通道失败时自动回退到另一条已登记且可达的通道。
7. 只有所有正式通道都不可达时，才显示连接异常，并给出用户可执行的恢复提示。

## 已否决的错误方向

曾考虑通过 ADB 建立 `tcp:4319` 正向映射，让电脑使用 `127.0.0.1:4319` 访问手机 Hub。该方案只适合开发机临时诊断，原因如下：

- 普通用户不会长期连接 USB 数据线。
- ADB 需要开发者选项和 USB 调试授权。
- 多台 Android 设备连接时无法安全确定目标设备。
- 该通道无法覆盖真实跨网络使用场景。
- 使用 ADB 验收会掩盖 Anywhere 或 LAN 自动连接的产品缺陷。

因此不得把 ADB 端点注册为生产环境高优先级 Hub 地址，也不得用 ADB 通道证明双 Hub 已达到发布标准。

- 检查手机本地 Hub 是否持续上报当前可用的 LAN 和 Tailscale 地址。

- 为端点记录增加最近成功、最近失败、连续失败次数和最后验证时间的明确使用规则。

### 本轮已完成

- 手机健康心跳发送前会重新读取 Android Local Hub 状态，使网络接口变化后的 LAN/Tailscale 地址进入当前心跳。
- 电脑端接收手机端点完整快照时，对未变化地址执行原地更新，保留最近成功、最近失败和连续失败次数。
- 当前快照中已经消失的地址会被及时删除，避免离开旧 Wi-Fi 后持续等待失效 LAN 地址超时。
- 生产界面和 README 已移除 USB 自动连接描述；ADB 仍只用于开发安装、日志和诊断。
- 打包桌面端不再自动建立 `adb reverse`；开发环境也只有显式设置 `AETHERX_ADB_REVERSE=1` 时才启用该辅助通道。
- Windows 安装器会创建仅限专用网络、本地子网、TCP `4318` 和 AetherX 安装程序路径的入站规则，卸载时删除；不会为公用网络开放 Hub。
- 桌面连接中心会识别当前 Windows 网络类别；公用 Wi-Fi 阻止 LAN 时提示把可信家庭网络设为专用或启用 Anywhere。
- 新增端点历史保留和异步健康快照测试。
- 全量自动化测试、最新安装包部署及无 ADB 映射的同一局域网真实往返已经通过；蜂窝网络/Anywhere 仍待验收。

### 自动选路与恢复

- 并发或快速顺序探测 LAN 与 Anywhere，不依赖固定地址。
- 优先选择最近成功且当前可达的正式端点。
- 当前端点失败后自动切换备用端点，并恢复复制调度。
- 手机从 Wi-Fi 切到蜂窝网络、Tailscale 重连、应用进入后台后，都要重新评估路由。
- 电脑重启、手机重启和 Hub 切换后，不能依赖旧进程内存恢复连接。

### 状态展示

- “已同步”要求两端序列一致、待同步媒体为零且当前存在可达的正式链路。
- “同步中”显示当前阶段、进度和目标 Hub。
- “连接异常”显示失败的是 LAN、Anywhere 还是两个通道全部不可达。
- 不把 USB/ADB 显示为普通用户可用的连接方式。

## 最终验收标准

以下项目全部通过后，才能给出“可以正式发布”的结论：

1. 新用户从全新安装开始，不输入地址，一次配对完成手机客户端和手机 Hub 的关联。
2. 同一 Wi-Fi 下，LAN 自动发现、登录、同步、切换和回切全部通过。
3. 手机关闭 Wi-Fi，仅使用蜂窝网络和 Anywhere 时，双向同步、切换和回切全部通过。
4. 全程断开 USB，且关闭所有 ADB forward/reverse 后重复第 2、3 项。
5. 手机 Hub 和电脑 Hub 分别作为活动 Hub 时，客户端都自动路由到当前活动 Hub。
6. 每次切换后两端 `epoch`、`active_node_id`、`state` 和 `transition_id` 一致。
7. 每次切换后复制序列一致、lag 为 `0`、待同步媒体为 `0`，复制健康状态稳定为 `healthy`。
8. 切换中断网、杀进程或丢失提交响应后，应用重启能够自动恢复到 `stable`。
9. 覆盖安装桌面端和手机端后，登录、历史会话、配置、Hub 身份和复制游标均保留。
10. 旧版本覆盖升级、新安装、注销重登、设备删除和重新配对均无阻断错误。
11. 自动化全量测试、桌面安装包验证、Android Release 构建及真实设备冒烟测试全部通过。
12. 连续运行观察期间不重复创建切换事务，不出现假“已同步”，也不持续误报“连接异常”。
